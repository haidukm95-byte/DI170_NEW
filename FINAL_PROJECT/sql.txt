Database Logic Overview
Lookup / Reference Tables
These are static, read-only tables seeded with fixed data. External users can only 
SELECT from operation_codes.

operation_codes — 15 operation types grouped into 4 categories: receiving (10–14), 
departure (20–24), utilization (32–36)

occupation_codes — 3 roles (Manager, Receiver, General worker), each with auth_receive 
and auth_edit_personnel permission flags


Core Data Tables

Table	Purpose

goods_registry	Master catalogue of all items. Every item that can ever appear in 
logistics must be registered here first. Codes must be 6 digits (100000–999999).

foods_inventory	Live stock levels for food/drink items. Updated automatically by 
triggers.

general_inventory	Live stock levels for general items. Updated automatically by 
triggers.

personnel	All staff records, linked to their occupation and permissions.

logistics	Every stock movement event. The central operational table — one row per 
operation.

What happens on INSERT INTO logistics
The user only provides: code, quantity, operation_code, responsible_id. 
Everything else is automatic:


BEFORE INSERT (alphabetical trigger order):
  1. before_logistics_check_registry   → blocks insert if code not in goods_registry
  2. before_logistics_set_goods_info   → fills name, is_food, measuring_unit from goods_registry
  3. before_logistics_set_operation_name → fills operation_name from operation_codes
  4. date_and_time                     → filled by DEFAULT CURRENT_TIMESTAMP

Row is written to logistics

AFTER INSERT:
  5. after_logistics_insert → updates inventory:
       is_food = TRUE  → foods_inventory
       is_food = FALSE → general_inventory

       op 10       → add quantity (INSERT new item or increment existing)
       op 20/32–36 → subtract quantity
       op 11–14,
          21–24    → no inventory change (goods were refused/returned)

AFTER UPDATE on inventory (if quantity changed):
  6. check_zero_quantity_food / check_zero_quantity_general
       → if quantity ≤ 0, item row is deleted from inventory
Integrity Rules
logistics.code must exist in goods_registry (FK + custom trigger with readable error)
logistics.operation_code must exist in operation_codes (FK)
logistics.responsible_id must exist in personnel (FK)
foods_inventory.code and general_inventory.code must exist in goods_registry (FK)
personnel.occupation_code must exist in occupation_codes (FK)
All code values across all tables must be 6-digit integers (CHECK constraint)
In one sentence: the database tracks a goods warehouse — every stock movement is logged in logistics, which automatically classifies the item, records who did it and when, and keeps foods_inventory / general_inventory stock counts up to date, deleting items that reach zero.
