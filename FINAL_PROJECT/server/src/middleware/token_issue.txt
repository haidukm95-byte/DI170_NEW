Good news: this isn't a Postman quirk — it's inherent to how JWTs 
work, and it's not a bug either, just a gap between what you have 
(fixed-expiry access token) and what you asked for 
(sliding/inactivity-based expiry). Let me walk through why, then 
implement the fix.

Why this happens: signAccessToken (authController.js:14-27) 
bakes exp = iat + 15m into the token at the moment it's issued. 
A JWT is a self-contained, signed blob — there's no way to "extend"
one that's already been handed out; the only way to get a later 
expiry is to issue a brand new token. So "expires in 15 minutes" 
currently really means 15 minutes after login/refresh, full stop, 
regardless of activity in between. Postman isn't doing anything 
wrong — no HTTP client (Postman, a browser, curl) has any concept
 of "user activity"; that's purely something an app has to track 
 and act on by calling your API. A real frontend without a 
 "silent refresh" timer would hit this exact same wall.

What "15 minutes of inactivity" actually requires, and what I'll 
build now vs. what needs the frontend:

Backend (buildable and testable now via Postman): right now, 
refresh() blindly trusts the refresh-token cookie for its full 
7-day life — a user who vanishes for 3 days and comes back can 
still silently mint a new access token. That's not "15 minutes of 
inactivity," that's "7 days no matter what." I'll cap it: track 
how long it's been since the session was last renewed 
(refresh_tokens.created_at, which already gets reset on every 
rotation, authController.js:104-109), and reject /refresh 
outright if that gap exceeds 15 minutes — forcing full re-login.
Frontend (can't build yet, no frontend exists): for the user to 
ever experience "stays logged in while active," the frontend must 
call POST /api/auth/refresh on a timer while the user is 
interacting with the page — comfortably before the access token's 
15-minute mark (e.g. every 10–12 minutes), typically gated by 
real activity listeners (mousemove/keydown/click) so a genuinely 
idle tab stops renewing. This is the standard "silent refresh" 
pattern for SPAs. Without it, every access token will hard-expire 
at 15 minutes flat, active or not — that part is unavoidable and 
correct JWT behavior, not something the backend can paper over.


AFTER EDITING
Done. In authController.js:94-102, refresh() now compares Date.now()
 against session.created_at (which gets reset to "now" on every 
successful rotation, so it always reflects the last time the 
session was renewed). If more than ACCESS_TTL_MS (15 minutes) 
have passed since the last renewal, the refresh token is revoked 
and the request gets 401 { error: 'Session expired due to inactivity' } — 
no more silently minting a new access token after hours or days 
away.

You can test this in Postman right now without a frontend:

POST /api/auth/login → get accessToken + refreshToken cookie.
Immediately POST /api/auth/refresh → should succeed (fresh tokens,
 201/200).
Wait 15+ minutes without calling /refresh, then call it again → 
should now get 401 Session expired due to inactivity.
If you call /refresh every, say, 10 minutes in a loop instead, it 
should keep succeeding indefinitely — proving the session survives
 as long as something renews it within the window.

!!!IMPORTANT!!!
That last point is the crux of what's still missing: nothing 
calls /refresh for you. Once the frontend exists, wire up a timer 
(or activity-driven timer) there that calls /refresh every ~10–12 
minutes while the user is interacting with the page — that's what 
turns "15 minutes since last renewal" into "15 minutes of real 
inactivity" from the user's point of view.
